## GitHub и доставка

GitHub Secrets для LLM и Telegram пока отсутствуют, доставка не подключена.
Variables: `REGION=tyumen`,
`DASHBOARD_URL` из таблицы, согласованный
`LLM_PROVIDER` и параметры модели/отбора по действующей схеме проекта.

Минимальные обязательные GitHub Secrets для доставки через `replay_on_push.yml`:

- Ключ согласованного LLM-провайдера: `OPENROUTER_API_KEY` при
  `LLM_PROVIDER=openrouter` либо `ANTHROPIC_API_KEY` при `LLM_PROVIDER=claude`.
  Если Variable `LLM_PROVIDER` не задана, этот workflow использует `openrouter`.
- `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID_TEST`.

Для Web Push дополнительно нужны `PUSH_WORKER_URL`, `PUSH_SECRET` и
`VAPID_PRIVATE_KEY`; без них Web Push пропускается. Эти значения требуется
задать в GitHub отдельно: Secrets Worker автоматически туда не передаются.
GitHub Secret `PROGRESS_SECRET` необязателен при наличии `PUSH_SECRET`:
ручной `update_cases.yml` использует `PUSH_SECRET` первым для публикации прогресса.
Это не отменяет отдельный `progress_token.tyumen` на VPS.
Для резервного LLM добавить соответствующий ключ.

`TELEGRAM_CHAT_ID_TEST` — существующий **личный чат пользователя с ботом**.
Секрет корпоративной доставки `TELEGRAM_CHAT_ID` не требуется и не переносится
из другой территории: production replay использует `TELEGRAM_CHAT_ID_TEST`,
а ручные workflow при отсутствии группового секрета также выбирают личный чат.
Согласована доставка только пользователю.

Первоначальные данные предоставляют операторы. Не запускать массовый сбор
истории или рассылку в другие чаты в качестве проверки подключения.

На 20.09.2026 вход `root` по ключу Mac через SSH работает. Причина прежних
отказов входа по паролю — `PermitRootLogin without-password` на сервере.

В `/opt/court-monitor` создан `dashboard-tyumen` (`main`, `3c39615`);
сохранены `dashboard`, `dashboard-ural`, `dashboard-bashkortostan` и `backups`.
Четыре таймера `court-*` проверены: `enabled`, `active (waiting)`.
В списке `territories` сохранены прежние три территории; Тюмень не добавлена
и остаётся неактивной до готовности доставки.

Для репозитория Тюмени создан отдельный deploy key. Пользователь подтвердил
право записи. После восстановления сети GitHub запросил `Confirm access`:
сохранение ключа ожидает подтверждения входа владельцем. Проверка
`git push --dry-run` с VPS до сохранения вернула отказ по ключу; доступ
к публикации пока не подтверждён. На VPS сохранена резервная копия SSH-конфигурации;
настройка выбора `deploy_tyumen` только для нового клона установлена и проверена:

```sshconfig
Match host ssh.github.com exec "test $(pwd) = /opt/court-monitor/dashboard-tyumen"
  IdentityFile ~/.ssh/deploy_tyumen
  IdentitiesOnly yes
```

В `~/.config/court-monitor` созданы региональные файлы с правами `0600`:

- `env.tyumen`: `REGION=tyumen`, `DASHBOARD_URL` из таблицы, `BANK_TRACK=1`
  и разрешённые параметры отбора из конфигурации Башкортостана.
  Токены Telegram/VAPID сюда не добавлять.
- `worker.tyumen`: собственные `url=`, `owner_secret=`, `push_secret=`;
  файл читается как данные, не через `source`.
- `progress_token.tyumen`: отдельный токен прогресса Тюмени.

После сохранения deploy key и подготовки доставки добавить путь клона
в `territories`, сохранив действующие территории. Для общего файла `telegram`
со служебными алертами проверить личного получателя; не менять получателей
других территорий попутно. Секретные файлы не попадают в Git. В копии проверить
настройку `merge.ours.driver=true`. Mac не включать вторым автоматическим
исполнителем. Устройство служб описано в общем [VPS README](README.md).
